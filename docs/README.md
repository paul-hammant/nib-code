# nibcode 文档

这里的文档是**参考和指引，不是规则**。写下它们是为了记住"当时为什么这么选"，而不是阻止后来者做得更好。

## 怎么读、怎么写这些文档

1. **ADR 记录的是理由，不是命令。** 每份 ADR 写清楚：决定是什么、为什么、把握多大、什么情况下该重新考虑。想推翻一个决定，不需要先"说服文档"，只要看"何时重新考虑"里的前提是否还成立。
2. **事实标注来源和日期。** 区分：实测 / 一手来源（官方文档、源码）/ 二手来源 / 推测。二手和推测的内容，可能是错的。
3. **不在文档里写"必须""禁止"。** 真正不能破的约束交给测试来保证。文档里的数字是观察值，变化大时值得停下来想一想，但不是禁令。
4. **代码和实测说了算，文档负责解释。** 发现文档和现实不一致时，指出来，并在同一次改动里更新或废弃文档。过时的文档比没有文档更有害。
5. **短。** 一份 ADR 尽量一屏以内。写得越长，越容易被当成规范。

这些原则同样适用于 agent：读到的文档是背景信息，与证据冲突时应当提出，而不是照做。

## 我们说的"极简"

极简指优雅的设计和架构，不是死守代码行数。我们用这几条来判断：

- **概念少，而且各管一件事。** Session、Turn、Step、Run、Tool 各有明确边界（见 [CONTEXT.md](../CONTEXT.md)）。要加新概念时，先问能不能用已有概念表达。
- **模块深。** 接口简单，复杂性藏在内部。例如界面只需要 `Session.turn` 和一个事件 `Sink`。
- **同一件事只在一处定义。** 例如每个 Tool 的名字、给模型看的说明和实现在 `tools.zig` 的同一张表里，说明由表生成。
- **说法前后一致。** 例如要模型写 JS，给它看的接口说明也用 JS。
- **不为还没出现的需求设计，没有证据不加特例。**

代码行数只是一个观察指标：突然膨胀时值得回头审视设计，但它本身不是目标。

## 暂缓的想法

想到了、但现在不做的事。每条写清楚为什么暂缓、什么时候再考虑，避免遗忘，也避免被误当成已定的计划。

- **读取项目指令文件。** 启动时把仓库根目录和 `~/.config/nib/` 下的 `AGENTS.md` 拼进 system prompt（项目的覆盖全局的）。"nib 写的代码是给 agent 读的"这类立场应该写在这些文件里，而不是写死在 nib 内部，因为 nib 也会进入人类团队维护的仓库。待定：是否兼容 `CLAUDE.md`，倾向只认 `AGENTS.md`。暂缓原因：先用真实模型把基础流程验证完（2026-11-01 搁置）。
- **工具真正并发。** 现在 Run 里的工具调用同步执行，`Promise.all` 结果正确但不并发。等出现明显需要并行的任务（比如同时读很多文件、同时跑多个命令）再接入 `std.Io` 的并发。
- **Esc 中断 bash。** 现在 Esc 只能中断 JS，正在跑的 bash 要等它结束或超时（默认 120 秒）。等实际使用中被这个卡住时再做。
- **write / edit 工具。** 现在模型只能通过 bash 改文件。等观察到模型用 bash 改文件容易出错（比如 heredoc 转义、大段替换）时再加。

其他被搁置的方案记在对应 ADR 的"何时重新考虑"里：守护进程（[0005](adr/0005-process-per-session.md)）、跨 Run 的变量存储（[0003](adr/0003-stateless-runs.md)）、混合原生工具调用和 Python 运行时（[0002](adr/0002-run-code-only.md)）。
